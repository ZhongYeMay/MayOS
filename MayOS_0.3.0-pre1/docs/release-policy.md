# MayOS 发布约定

## 发布节奏（2026-11-11 起）

**开发与发布解耦。** 普通代码提交、Bug 修复、网页改动与持续集成不会自动提升 `preN`，也不会创建新的 GitHub Release。只有一组具有实际价值的改进完成后，才手动准备并发布新版本。无需为了每次小改动额外创建预发布版。

建议的发布门槛：

1. 累积多项可以在更新说明中清楚解释的功能改进或修复，或完成一项重要阶段性功能；纯格式修改、文档更新和修复 CI 脚本通常不单独形成新版。
2. 与变更对应的自动构建、单元/集成测试通过。影响引导、图形或存储时，需重新执行对应的 BIOS / UEFI 和 QEMU 客体测试。
3. 若宣称发布可启动的系统版本，必须有同一源码版本生成的 ISO、实际验证记录与 SHA-256；不以网页演示、旧录像或之前版本镜像冒充验收。
4. 发布说明列出这一批累计的功能、修复、已知限制和验证范围；手动确认准备发布后才打版本号。

## 操作流程

- 持续向 `main` 提交开发修改，正常进行构建、测试和代码审查；`MayOS_0.3.0-pre1/VERSION` 可暂时保持同一个开发版本，不等于已经公开发布。
- 认为一批改进达到上述门槛时，在 GitHub Actions 手动运行 `Increment MayOS prerelease version`，填写改进摘要并将 `confirm` 设为 true。每次手动操作**只增加 1 个 `preN`**，不按提交数增加。
- 检查版本同步（`VERSION`、GUI、Linux 模式）及源码 CI。之后才按实际发布内容手动运行 `Publish MayOS source prerelease` 或完整带启动测试的发布工作流。
- `Publish validated MayOS 0.4.0-pre63 ISO` 属于历史 pre63 的补充附件工作流，保留手动触发，不因推送配置文件而再次发布。
- 正式版同样必须手动触发构建、校验、发布；不允许提交工作流配置文件自动发布正式版。
- **所有历史 GitHub Releases 都保留**，不自动删除旧版。官网在正式发布新版本后更新其发布入口；代码持续开发不意味着每次都要更新版本页面。

- 已存在的 `v0.4.0-preN` 历史标签和 Release 不改名、不删除，以免与历史版本冲突。

## 版本号

- 预发布版：`v主版本.次版本.修订版本-preN`（如 `v0.4.0-pre63`）；每批达到发布门槛后才递增。
- 正式版：`v主版本.次版本.修订版本`，不带 `pre`。重要功能集通常提升次版本号；不兼容的大改动提升主版本号。
- 不使用 `-source.1` 等二次后缀；若只发布源代码，必须清楚标记 **source-only**，不得暗示 ISO 已验证或附上旧镜像。
- 以 GitHub Releases 的实际附件与标签为已发布事实，不以源码中的版本常量推断新发行包存在。
